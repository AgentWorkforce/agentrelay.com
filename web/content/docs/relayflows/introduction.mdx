title: 'Relayflows'
description: 'A deterministic script over agentic primitives — steps you can inspect, verify, and resume, not a prompt and a hope.'

Relayflows turns a coding-agent task into steps you can inspect and verify. A flow combines shell commands, model calls, and coding agents with a journal that records what each step did and why it completed. Start with a small local flow; add verification as the task grows.

Every effect is journaled before it's real. If a step's write to that journal fails, the step fails — there's no silent fallback and no "it probably worked." That's the trade Relayflows makes everywhere: less magic, more evidence.

## The ladder

Every flow is built from the same small set of rungs, and you only climb as high as the task needs:

1. **`run`** — a shell command. No model anywhere.
2. **`llm`** — a bare model call. Prompt in, verified output out — no workspace, no tool use.
3. **`agent`** — a harnessed coding agent in a workspace. Returns an artifact, not just text.
4. **`human` / `dispatch` / `done`** — durable approval, handing work to a child flow, and a typed finish.

Most flows on day one are just `run` and `llm`. `agent` is the rung you climb to when the step needs hands on a real workspace.

## A whole flow

```ts
import { flow } from '@relayflows/surface';

export default flow('hello', async (f) => {
  const greeting = await f.run('echo "Hello from Relayflows"');
  console.log(greeting.trim());

  const answer = await f.agent('greeter', {
    task: 'Reply with one short hello sentence. Do not use tools or modify files.',
  });
  console.log(answer.summary);

  f.done('success');
});
```

`f.run` executes a shell command and returns its output. `f.agent` hands a task to a real coding-agent CLI in a workspace and returns `{ summary, artifacts }` — not a raw transcript. `f.done` closes the run with one reason from a closed set: `success`, `step_failed`, `canceled`, or `budget_exceeded`. There's no fifth option a caller has to guess about.

## Verification instead of vibes

An agent's failure mode is wrong output, not no output — a retry built for "it crashed" doesn't catch "it returned something plausible and wrong." So a step's completion isn't the agent's opinion; it's a check the kernel runs on what came back.

```yaml
version: '0.1.0'
name: hello-agent
steps:
  - id: greet
    type: deterministic
    command: 'printf hello'
    verification:
      type: output_contains
      value: hello

  - id: edit
    type: agent
    dependsOn: [greet]
    instruction: 'Produce the hello artifact.'
    recoveryMode: reset
    maxIterations: 2
    permissions:
      fileGlobs: ['artifacts/**']
      accessPreset: readwrite
    verification:
      type: output_contains
      value: agent-ok
```

Every step's exit code is checked automatically; `output_contains` is an opt-in accelerator on top of it, and an `llm` step can require its output to match a `json_schema` instead. A step that fails verification doesn't get to report success — it's `verification_failed`, journaled, visible.

`recoveryMode: reset` is the agent step's crash contract: if this step dies mid-edit, the next attempt starts from the pinned workspace revision, not from whatever half-finished state was left behind. `permissions` bounds what that attempt can touch while it runs.

## Resumable by construction

Kill the process mid-run and start it again — completed steps aren't re-executed, and their effects aren't re-sent:

```text
$ npx --no-install flows run hello.flow.ts --local-agent --input '{}'
○ run-1 (deterministic) 0.00s
✓ run-1 (deterministic) 1.02s completionReason: success
Hello from Relayflows
○ agent-2 (agent) [agent: preparing] 0.00s
↻ agent-2 (agent) [agent: running] 12.51s
✓ agent-2 (agent) [agent: completed] 28.95s completionReason: success
Hello! How can I help you today?

RUN 01M20JYM4T9FNGNFX4NQCK34JK completed (3 steps) completionReason: success
```

That's a real captured run, not a mockup — every step carries a `completionReason` from a closed vocabulary (`success`, `verification_failed`, `retries_exhausted`, `lease_expired`, `crashed`, `timeout`, `worker_error`, `budget_exceeded`, `canceled`), so a run's journal always says which of those it was. No raw stack trace ever stands in for one.
