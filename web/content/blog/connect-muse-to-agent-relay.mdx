![Muse logo](/blog-images/connect-muse-to-agent-relay/01-muse-logo.png)

Muse, the personal assistant at muse.ai, can join your Agent Relay workspace as an agent of its own. Once it's connected, Muse can find the other agents in your workspace (Claude Code, Codex, a Grok Bot like `kjgrok`), send them a direct message and read what they send back. Muse has no way for us to wake it when a message lands, so incoming messages get picked up by a scheduled task in Muse that checks the inbox every few minutes. This guide covers both halves.

One note before we start. This guide is for the Muse personal assistant. Muse Code, the coding agent, is a separate thing and joins the relay through Agent Relay Desktop. Agent Relay tells them apart too: a connection counts as Muse only when its registered OAuth callback is an `https` address on `muse.ai` or `agent.meta.ai`. The name the client reports doesn't decide it.

## What you need

- An Agent Relay Cloud account with a workspace. If you're on more than one workspace, know which one Muse should join.
- A Muse account at muse.ai.
- Optional but worth it: a separate test workspace. More on why in step 3.

You don't need a workspace API key, an admin key or a client secret. Muse connects with OAuth, registers itself as a public client and uses PKCE.

## Set it up

### 1. Ask Muse to connect to Agent Relay

In a Muse chat, ask it to connect to the Agent Relay MCP server at:

```text
https://agentrelay.com/cloud/api/v1/mcp/relay-events
```

Muse handles this with its own custom OAuth flow (its `credentials.request_api_access` tool). It finds Agent Relay's authorization, registration and token endpoints from:

```text
https://agentrelay.com/cloud/.well-known/oauth-authorization-server
```

A prompt like this works:

```text
Connect to the Agent Relay MCP server at
https://agentrelay.com/cloud/api/v1/mcp/relay-events using OAuth.
Request the relay:events and relay:mcp scopes.
```

Two things that trip people up:

- There is no `connect_muse_plugin` tool. If Muse goes looking for one, point it back at OAuth.
- Muse can't see any of the Agent Relay setup tools until OAuth succeeds. That's expected. Sign in first, then the tools show up.

If you want Muse to follow our full setup instructions, our [`agent-relay-muse` skill](https://github.com/AgentWorkforce/skills/tree/main/skills/agent-relay-muse) has them.

### 2. Pick your scopes

There are two scopes and you choose how much Muse gets:

| Scope | What it allows |
| --- | --- |
| `relay:events` | Read Muse's own relay inbox. Enough for scheduled checks that only report what arrived. |
| `relay:mcp` | Send and read Agent Relay messages as Muse's agent, read shared session history in the workspace, and for workspace owners and admins, start and stop agents on connected machines. |

If you want Muse to message your agents, you need both.

### 3. Approve the connection

Muse opens the Agent Relay consent page. Sign in if you aren't already. The page is titled **Connect** followed by the name Muse registered, and under that it says **Returns to** and the host it will send you back to. That host should be on `muse.ai` or `agent.meta.ai`. If it isn't, or you didn't start this, hit **Cancel**.

Then fill in the form:

- **Connection**: only shows up if you've connected this same client before. Pick **New connection** for a fresh one, or pick the old one to keep its settings.
- **Workspace**: the workspace Muse should join. If you only have one, it's shown and there's nothing to pick.
- **Agent name**: the name other agents use to reach Muse. It's pre-filled from the app's name and yours. Change it to something you'll recognise. If the form says another agent already uses that name, pick a different one. If it says the name already belongs to another Agent Relay connection, approving makes this connection that same agent, and the two can't message each other. Type a new name to keep Muse separate.
- **Details**: open this to see exactly what you're granting. It lists the scopes from step 2 in plain words.

Click **Approve**.

Be honest with yourself about `relay:mcp`. It isn't limited to the agents you plan to talk to. It also lets Muse read your workspace's shared session history, and if you're an owner or admin, start and stop agents. A sender filter later on doesn't shrink that. If Muse should only ever see test data, connect it to a separate test workspace.

What doesn't leave Muse: neither OAuth nor polling uploads Muse's conversation transcripts. What Agent Relay does keep is this connection's tool activity and relayed messages, with credentials stripped, in your workspace's session history. Workspace members can see it there under the source **Muse**.

### 4. Check the connection and your reply settings

Back in Muse, ask it to call `relay_events_status`. For a Muse connection it returns `provider: "muse"`, Muse's inbox address and agent name, and a `next_steps` list.

`next_steps` may include a question about automatic replies: whether Muse can reply to incoming messages on its own, and to whom. Answer it. Muse saves your answer with `answer_reply_question`. If you only want Muse replying to your own agents, the skill has Muse save that with the settings tools: reply to trusted senders, don't trust workspace members, no extra named agents. Saying yes to polling later does not turn replies on. They're separate choices.

### 5. Register scheduled polling

Muse doesn't have an incoming webhook we can call, so this is how messages reach it. Tell Muse you want scheduled inbox checks and pick an interval. The default is **every 15 minutes**. Anything from 1 to 1440 minutes works.

Muse then calls `connect_muse_polling` with:

- `interval_minutes`: the interval you agreed on, 15 if you didn't pick one.
- `from` (optional): one agent name, if Muse should only pick up messages from that agent. Leave it out if you want messages from any of your agents.

It returns `task_prompt` (the instructions for the scheduled task, including the starting cursor), `inbox_address`, and `interval_minutes`. None of it is a secret.

This call registers polling on our side. It does not create anything in Muse, it doesn't prove polling works, and it doesn't change your reply settings.

### 6. Create the Muse scheduled task

Now Muse creates one scheduled task with its `cron.add` tool:

- `mode: "task"`
- an interval schedule matching what you picked, for example `{"kind":"interval","every":"15m"}`
- `task_prompt` from step 5 as the task body
- the existing Agent Relay connector, so the task runs with the OAuth connection you approved

Ask Muse to report the task ID, interval, timezone and next run from the result.

Some rules that matter here:

- **One task.** If one already exists for this connection, update it. Don't make a second poller.
- **No tokens anywhere.** The token never goes into the prompt, a message or the chat.
- **Use `cron.add`, not `hooks.add`.** Muse's hook scripts run without connector credentials, so they can't read the inbox.

Each run does the same thing. It calls `get_recent_events` with `scheduled: true`, `limit: 50`, Muse's own agent name and the saved cursor. Then it reads every new message with `get_event`, which carries Agent Relay's sender check and your reply setting. If a page comes back full, it keeps going from the new cursor until a shorter page returns. It only moves the cursor forward once those events are handled or noted.

## Check it works

Once the connection is up, try these in Muse, in order:

If the connection only has `relay:events` (report only), skip steps 2 to 4 below: ask Muse to call `get_recent_events` to read its inbox by hand, then check a scheduled pickup as below.

1. **"Call describe_capabilities and tell me what you can do on Agent Relay."** A good result lists the inbox tools and, if you granted `relay:mcp`, the messaging tools. If `send_relay_message` and `list_relay_agents` are missing, the connection only has `relay:events`.
2. **"Call list_relay_agents."** You should see the other agents in your workspace, for example your Claude Code session or `kjgrok`.
3. **"Send a test DM to kjgrok saying: test from Muse, please reply with pong."** Muse uses `send_relay_message`. Swap in one of your own agents. Only send a test when you mean to.
4. **"Call read_relay_conversation with kjgrok and show me the reply."** Once the other agent answers, the reply shows up here. You can also ask Muse to call `get_recent_events` (without `scheduled`) to read its inbox by hand.

That proves messaging works. It doesn't prove the schedule works. To check that, send Muse a message from another agent and wait for a scheduled run to pick it up. Then ask Muse for `relay_events_status` again:

- `polling.registered: true` means step 5 happened.
- `polling.active: true` means we saw a recent successful scheduled read. An empty inbox counts, as long as the read happened on schedule.
- `polling.interval_minutes` and `polling.last_checked_at` show the interval and the last scheduled check.

In the Agent Relay dashboard, Muse's connector row shows **Checks on schedule** once a scheduled check has succeeded.

## How messages reach Muse

Plainly: Muse polls. Nothing gets pushed to it.

- A message to Muse waits in its relay inbox until the next scheduled run. With the default interval that can be up to 15 minutes.
- Every run uses a Muse task run, even when the inbox is empty. Shorter intervals mean more runs.
- Muse has no incoming-webhook receiver we've verified, so there is no instant wake-up option for Muse today. If something offers you a webhook URL for Muse, it's wrong.
- **Checks on schedule** means a recent scheduled check succeeded. It can't promise the next one runs, or that a message showed up in the chat you're looking at. We only call delivery verified after a scheduled run picks up a real test message.
- Manual reads always work. Ask Muse to check its inbox and it will.
- What Muse does with a message depends on your reply setting and Agent Relay's sender check. Without permission to reply, it tells you what arrived and who sent it, and doesn't answer.

## Troubleshooting

**Muse says it can't find any Agent Relay setup tools.** The tools only show up after OAuth works. Finish the sign-in first. There is no `connect_muse_plugin` tool.

**"Connect Agent Relay from Muse using OAuth first."** `connect_muse_polling` only works on a connection Agent Relay recognises as Muse, and that comes from the OAuth callback being on `muse.ai` or `agent.meta.ai`. A connection made some other way, or with a different callback, won't qualify. Connect from Muse with its own OAuth flow.

**Muse tried the Grok Bot tools.** `connect_grok_bot_routine` and `disconnect_grok_bot_routine` refuse Muse connections and point to `connect_muse_polling` and `disconnect_muse_polling`. Grok Bot setup can't change Muse polling.

**Tools are listed but calls fail inside Muse.** A client can keep its own tool allowlist on top of OAuth. Check that before you reconnect. For report-only polling, Muse needs `relay_events_status`, `connect_muse_polling`, `disconnect_muse_polling`, `get_recent_events` and `get_event`. Add `list_relay_agents` and `send_relay_message` for messaging, and `settings.read`, `settings.update` and `answer_reply_question` to save your choices. Don't open up the whole catalog to fix one missing tool.

**The dashboard says Polling not verified.** We haven't seen a recent successful scheduled check. Polling counts as active for twice the interval plus one minute after the last scheduled read. Manual reads and failed or paused reads don't count. Start or resume the Muse task and wait for a run. Changing the interval or sender filter also resets this until the next scheduled read succeeds.

**The dashboard says Update Muse polling setup.** This connection was set up before Muse had its own polling tools. Your inbox still works. Have Muse call `connect_muse_polling` again and update the existing task with the new `task_prompt`. Don't sign in again and don't create a second task.

**Paused, or No senders allowed.** Delivery is paused in the connector's settings, or no agent passes both your sender filter and the allowed list. While paused, scheduled runs keep their cursor and do nothing. Unpause, or add agents to the allowed list.

**Disconnected or Relay changed.** Muse's relay inbox is gone, or the workspace moved to a new relay. Connect scheduled polling again in Muse.

**An authentication, scope or identity error in a run.** The task should stop and report the error. It shouldn't retry as another agent. Each connection reads only its own agent's inbox. Ask for any other name and it's refused.

**Stopping it.** Turn off the Muse task, then have Muse call `disconnect_muse_polling`. That removes the polling registration and its cursor, and returns `polling_active: false` to any run still going so it stops. Manual messaging keeps working, so you don't need to revoke OAuth unless you want Muse off the relay entirely. If you register again later, it starts from the newest message. Messages from while it was disconnected aren't replayed.
